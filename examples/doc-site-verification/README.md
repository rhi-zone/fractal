# examples/doc-site-verification

Two real, minimally-scaffolded doc sites — a Docusaurus site
(`docusaurus/`) and a Starlight (Astro) site (`starlight/`) — that each
consume the REAL `toDocusaurusRouteReference`/`toStarlightRouteReference`
output from `@rhi-zone/fractal-http-api-projector` and run the REAL
`docusaurus build`/`astro build`, not a structural/mocked stand-in.

## What this is for

`packages/http-api-projector/src/http-route-reference.ts` and
`packages/api-explorer/`'s `<ApiExplorer/>` were previously verified only at
the component level (happy-dom render tests, generated-MDX-text parsing —
see `packages/api-explorer/src/api-explorer.test.tsx`/`end-to-end.test.tsx`)
— real code paths, but never run through an actual site build. This
directory closes that gap, the same way `packages/type-ir/src/
sphinx-reference.ts` got a real `sphinx-build` verification pass (see
`docs/roadmap.md`'s dated Sphinx write-up).

**Unlike the Sphinx pass, this fixture is PERSISTED, not ad hoc/throwaway.**
The project owner's call (see `docs/design/mocked-fetch-backend.md`'s dated
write-up for the full reasoning): Docusaurus/Starlight site scaffolding
involves several fiddly, easy-to-get-wrong wiring steps — theme swizzling
(Docusaurus `src/theme/Root.tsx`/`MDXComponents.tsx`), global MDX component
registration, Starlight component overrides, `@astrojs/react` island
wiring — that are worth NOT re-deriving from scratch the next time this
needs checking (e.g. after a future `http-route-reference.ts` change, or
when the next doc-projector target, VitePress/mdBook/DocFX, wants the same
kind of real-build check). Persisting costs disk/repo weight but no CI time,
since it's deliberately kept OUT of the default test loop (below) — the same
cost tradeoff Sphinx's ad hoc approach was managing, just resolved the
other way because the setup cost here is higher and the toolchain cost
(plain `npm`/`npx`/`bunx` against the registry, no new Nix packages) is
lower than Sphinx's `python3Packages.sphinx` flake addition.

## Why this is NOT in default CI/test

Both sites' `node_modules/`, `package-lock.json`, and build output
(`build/`, `dist/`, `.astro/`, `.docusaurus/`) are gitignored (root
`.gitignore`), and generated MDX (`docs/api/`, `src/content/docs/api/`) is
gitignored too — regenerated by `bun run generate`, not committed.
Neither site is listed in the root `package.json`'s `workspaces` array, and
neither site's `build`/`generate` script is wired into
`bun run --filter '*' test` or any package's own `test` script. This
mirrors the Sphinx pass's cost/footprint reasoning
(`docs/design/ci-pre-release-workflow.md` §2): a real `npm install` +
`docusaurus build`/`astro build` is minutes of work and network-dependent
(pulls from the npm registry), not something every push/PR should pay for.

## How to run it

Each site is an independent, plain-npm project — NOT a bun workspace
member — that depends on the real workspace packages via `file:`
dependencies (`@rhi-zone/fractal-api-explorer`, `@rhi-zone/
fractal-http-api-projector`, and their own transitive workspace
dependencies `@rhi-zone/fractal-api-tree`/`@rhi-zone/fractal-type-ir`,
pinned via both direct `file:` deps and an `overrides` block so a plain
`npm install` — which doesn't understand `workspace:*` — always resolves
every nested reference to the same local package). Because these are real
symlinked `file:` dependencies, `bun run build:packages` (repo root) must be
run first so `dist/` exists for each package.

```sh
# from repo root, once (or whenever packages/* source changes):
bun run build:packages

cd examples/doc-site-verification/docusaurus
bun run generate   # writes real generated MDX into docs/api/
npm install
npm run build      # real `docusaurus build` — output in build/

cd ../starlight
bun run generate   # writes real generated MDX into src/content/docs/api/
npm install
npm run build      # real `astro build` — output in dist/
```

`generate.ts` in each site builds a tiny fixture `OpenApiDoc` (one `GET
/books/{bookId}` with a path param, one `POST /books/add` with a request
body — enough to exercise both path-param rendering and request/response
schema embedding) from a shared fixture `Node` tree
(`src/fixture-tree.ts`, one per site — duplicated rather than shared across
the two site directories, since each is an independent non-workspace npm
project) via the REAL `toOpenApi`/`toDocusaurusRouteReference`/
`toStarlightRouteReference`.

Both sites are also LIVE-functional against that same fixture tree, not
just structurally present:

- **Docusaurus** (`docusaurus/src/theme/Root.tsx`): wraps the whole app in
  `ApiExplorerFetchProvider` with `toDropInFetch(createFetch(api))` — real
  React context, since Docusaurus renders as one client-side React tree.
- **Starlight** (`starlight/src/fetch-setup-client.ts` +
  `src/components/CustomHead.astro`): monkey-patches `window.fetch` once,
  before any page's islands hydrate — NOT React context (see
  `fetch-setup-client.ts`'s doc comment for why the Provider approach
  doesn't work across Astro's independently-hydrated `client:load`
  islands — a real finding from this verification pass, not a stylistic
  choice).

Every `<ApiExplorer/>`'s "Send" button therefore fires a real in-process
request against handlers that actually implement the documented routes.

## Real bugs this pass found and fixed

See `docs/design/mocked-fetch-backend.md`'s dated write-up (appended after
its "Resolved (2026-08-13): use case 2" section) for the full account —
summary: a bundler-eagerly-resolves-dynamic-imports bug in
`openapi.ts` that broke ANY browser bundling of `createFetch`/
`toOpenApiFromRoute` (not just callers using the `sourceFile` option that
triggered it), and an MDX curly-brace-escaping bug in
`http-route-reference.ts`'s Docusaurus renderer that crashed real
`docusaurus build` SSG on any route with a `{pathParam}` in its title.
