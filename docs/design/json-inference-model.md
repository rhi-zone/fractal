# Design document: a model-comparison foundation for JSON type inference

## 1. What inference *is*, formally

### 1.1 The problem statement

A corpus `V = (v₁ … v_N)` of JSON values is assumed drawn from an unknown data-generating process `P` that has a true-but-unobserved schema `S*`. Inference produces `Ŝ`. The current code has no stated objective at all — each pass optimizes an unnamed local criterion, and the passes' relative authority is decided by *ordering* in `resolveEvidence` (steps 2–7), with several documented as needing "first refusal" over the next. That ordering is a hidden arbitration mechanism with no criterion behind it. Any candidate formalism must, at minimum, put all decisions at a position on one comparable scale.

### 1.2 Facts, not hypotheses

§1.2 below (unchanged from the original version of this document, retained as groundwork) analyzes inference as a choice among competing **hypotheses** — candidate schema interpretations at a position, scored by likelihood or description length. That framing carries a problem it never states: hypotheses have to come from somewhere. Before a Bayesian posterior or an MDL score can rank "record over field-set F" against "map with value type V" against "enum over member set M," something has to have proposed exactly those candidates, in exactly that parameterization, out of an unbounded space of possible schema interpretations. The five-candidate survey answers *how to score* a fixed slate; it is silent on *how the slate gets built*.

A later round of design conversation (recorded in the discussion log at the end of this document) worked through a reframing that dissolves this gap rather than patching it: replace "hypothesis" with **fact**.

A fact is a deterministically-derivable statement about the corpus. "Sample 5 has key `main`" is a fact. "The distinct-key-count sequence across samples is `[3,9,13,16,17,18,18,19,20,20,20,20]`" is a fact — the same sequence the endpoint-ratio computation in §3's failure-1 discussion already discards after computing it. Crucially, a *score* is also just a fact: "the description length of the corpus under interpretation X is 340 bits" is a statement computed deterministically from simpler facts (the corpus, the candidate grouping, a code design), not a member of a separate, specially-scored category of object. There is exactly one kind of thing in this model — facts — built up from simpler facts by a single operation, **synthesis**, all the way from raw per-value evidence up through intermediate structural observations to the schema finally chosen.

This is why the hypothesis-enumeration problem dissolves rather than needing a separate answer: hypotheses need to be *proposed* — specified in advance, out of a space someone has to have bounded — before they can be scored. Facts don't need proposing. A fact about the corpus is either derived (because something upstream produced it, deterministically, from other facts already in hand) or it isn't yet in evidence. "What facts get derived, and in what order" is a real, still-open question (§1.3 below), but it is a *search/generation* question, not an *enumeration-of-a-fixed-hypothesis-space* question — the distinction matters because the latter requires bounding the space up front (which is where the original framing's "which of five sibling fields is the discriminant" awkwardness, noted for candidate (b) below, actually comes from), while the former only requires a rule for producing the next candidate fact from what's already known.

### 1.3 Synthesis is deterministic, content-addressed, and re-derivable

Synthesis — merging facts into more complex facts — is a pure, deterministic function of its inputs: the same set of input facts always synthesizes to the same output fact. This is the same property that makes git objects, Nix derivations, and Bazel's build graph work: content-addressed, deterministic, re-derivable computation. Two consequences follow directly, and both are answers to gaps the original version of this document flagged and left open.

**1. Structural sharing / position-independence.** If the same fact — "this position looks like an envelope-pattern DU keyed on `type`," say — is independently derived at two different tree positions, the two derivations are, *by content*, the same fact. They can be recognized and merged as such without an explicit graph of cross-position edges connecting the two positions. This directly answers a gap the original §4/§5 left as future work: composite/multi-field discriminants and cross-position dirty-data correlation (§2.2, point 4 below) were flagged as needing "graph edges" layered on top of the evidence tree. Under the fact model, facts are not required to be anchored to a single tree position at all — a fact can be scoped at whatever level actually applies to it: a single position, a single sample, or the whole corpus. Identical facts computed at different scopes collapse via content-equality, not via a separately-built graph. This is a real simplification, but see the caveat in §4.1a: *that facts can be scope-free is a property of the model, not yet a specification of how a given fact's correct scope gets assigned.*

**2. Bounded memory via re-derivation, not exhaustive storage.** Because synthesis is deterministic, the system never has to keep every intermediate fact materialized during search. A fact that isn't currently needed can be evicted and, if needed again later, recomputed from the same inputs — trading recomputation for memory, exactly as a build cache does. This is a direct, principled answer to the risk this document's §5 already flags under its own name ("search blowup... exponential if done naively") — not a bolted-on mitigation, but a consequence of the fact/synthesis model itself: memory bounds and search cost are no longer coupled to the size of a search *tree* held all at once, because the tree doesn't need to be held all at once.

**Two things this reframing does not yet resolve, stated plainly so they aren't mistaken for solved:**

- **Candidate generation.** Synthesis describes how facts *combine*; it does not describe how new candidate facts get *proposed* for consideration in the first place. Some generation/search mechanism is still needed — the difference from the original hypothesis-enumeration problem is that this mechanism only has to produce *one next candidate fact* from the facts already in evidence, not enumerate a bounded space up front; but a concrete generation strategy is still design work, not yet specified.
- **Eviction policy.** Determinism makes eviction *safe* — nothing is lost, because anything evicted is re-derivable — but it does not by itself say *when* to evict, i.e. what memory-pressure policy governs which facts get dropped and recomputed on demand versus kept resident. That's a tuning/engineering question layered on top of a now-safe primitive, not an answer this reframing supplies.

### 1.4 The stopping/refinement criterion: marginal entropy

Given facts and synthesis as the substrate, one question remains at every decomposition step: *should the current explanation be refined further, or is it good enough?* The refined framing's answer is a single, uniform criterion rather than a per-pass local statistic: **after conditioning on the current best explanation, how much residual uncertainty (entropy) is left in the data — and does that residual represent structure still being missed (refine further), or variation this level of explanation already accounts for (stop)?**

Walking through the same four failures diagnosed in §3, each one turns out to be an instance of exactly this question:

- **Failure 4, enum under Zipfian skew.** Does treating a position as "closed vocabulary of K values" actually reduce future uncertainty about unseen samples, or is the apparent low cardinality an artifact of undersampling — real residual entropy still hiding in unseen members? This is candidate (e) below (Good–Turing discovery-rate estimation) re-read not as a bolted-on estimator specific to enum detection, but as the general residual-entropy criterion applied at this one position: `f₁/N`, the discovery mass, *is* the residual entropy left over after committing to a closed vocabulary.
- **Failure 2, envelope-pattern DU.** Does conditioning on `type`'s value collapse `data`'s shape uncertainty to near zero? If so, `type` is a meaningful discriminant, not incidental variation. This is literally **mutual information** — how much conditioning on X reduces the marginal entropy of Y — and it directly replaces the flat `cohesion × separation` sibling-key heuristic that §3 found identically zero for the envelope pattern regardless of N. (§3's failure-2 discussion below is updated accordingly: the fix is characterized as mutual information between the candidate discriminant field and residual sibling-subtree entropy, not — as an earlier pass at this document put it, and as the project owner later flagged as not quite right — "recursive subtree description length" taken alone.)
- **Failure 1, dict-vs-record.** After conditioning on "this is a bounded N-field vocabulary," is there still real residual uncertainty in which fields appear per sample, or has it already plateaued? The growth curve flattening toward zero new keys — `f₁ → 0` in the per-sample key sequence — *is* residual entropy going to zero.
- **Failure 3, dirty data.** After fitting the schema's real variants, does the residual stay genuinely unexplained (high-entropy, noise-shaped), or would it collapse to near-zero entropy if simply admitted as a legitimate additional variant?

This does not compete with the MDL framing already developed below (candidate (d)); it identifies what quantity that framing should be computing at every decision point, uniformly. Shannon's source coding theorem says the expected optimal code length for a source equals its entropy — so residual/marginal entropy after conditioning on an explanation is exactly MDL's `L(V|H)` term, the cost of encoding the data *given* the explanation. And discriminant selection via entropy reduction is exactly mutual information, which is exactly the information-gain criterion a decision tree uses to pick a split — so the same quantity unifies MDL's "how many bits does this cost," Good–Turing's "how much of the vocabulary is still unseen," and decision-tree induction's "which field to branch on." What the original five-candidate analysis left as five formalisms scoring incomparable local statistics per pass (a K/N ratio here, a Jaccard distance there, a skew percentage elsewhere) resolves to one quantity, computed the same way, at every position.

### 1.5 Groundwork: five candidate formalisms

The analysis below predates the facts/synthesis/marginal-entropy framing in §1.2–1.4 and is retained because it is the groundwork that framing generalizes, not because it stands as a separate, competing proposal. Concretely: §1.4 above shows that MDL (candidate (d)), Bayesian posteriors (candidate (c)), and Good–Turing discovery estimation (candidate (e)) are all special cases or restatements of "reduce marginal entropy given the current explanation" — so this section's conclusions survive, reinterpreted as instances of the more general criterion rather than as independent choices among which one notation to standardize on.

**(a) Heuristic cascade (status quo).** "Confidence" is unrepresented; the only output is a boolean per pass, produced by comparing one or two summary statistics to a constant. Different passes' statistics live on incomparable scales (a K/N ratio, a Jaccard distance, a growth ratio, a skew percentage), so nothing can be traded off against anything else. The prior art is unanimously negative on this as a foundation, from three independent directions: Tagger's authors observed that "settings working well for one dataset yield poor results on another" and built a GUI specifically so users could watch thresholds fail (§1); quicktype's author calls the approach "not very scientific" outright (§3); JSONoid's own conclusion is that "heuristics to reduce overfitting remain unimplemented future work," with naive enable-everything overfitting at 42.6% (§4). **Handles none of the four failures**, by construction — all four are cases where a richer statistic was reduced to a scalar before the decision.

**(b) Frequentist hypothesis testing.** Null "this position is a record," alternative "map"; confidence = p-value, correctness = type-I error control. Genuinely fits failure 1 (a test of the growth curve against a fixed-vocabulary null is a real, standard test). Two structural problems: multiple testing (GitHub Issue alone has ~40 structural positions × 6 passes; family-wise error needs Bonferroni/FDR machinery that has no natural home in a tree walk), and — more fundamentally — testing *rejects* a null but does not *choose among* many non-nested alternatives. "Which of five sibling fields is the discriminant" is not a hypothesis test. **Fits failure 1; awkward for 2 and 4; wrong shape entirely for 3**, which is a mixture-estimation problem, not a test.

**(c) Bayesian model comparison.** At each position enumerate hypotheses `H` (record over field-set F, map with value type V, enum over member set M, union of k variants, DU conditioned on field f, …) and score `p(H | V) ∝ p(V | H)·p(H)`. Confidence = posterior probability, on one scale across all hypotheses at that position — which is precisely the property the cascade lacks. The priors are where configuration lives, and this is the formalism's honest answer to "hardcoding smells wrong": the constants don't vanish, they become *few, domain-meaningful, and user-owned*. This is directly what ptype does (§2): a column type is chosen by maximizing `p(t=k|x) ∝ p(t=k)·Πᵢ[π_k^k·p(xᵢ|k) + π_k^m·p(xᵢ|m) + π_k^a·p(xᵢ|a)]`, with the mixture weights hand-tuned but *stated as priors*, not buried in a threshold. **Handles 1, 3 and 4 naturally; handles 2 only if the hypothesis space is enlarged — see §3.**

**(d) MDL.** Score `= L(H) + L(V|H)` in bits; pick the shortest. Under a coding argument this is (c) with `−log p(H) = L(H)`, so it is not a competing theory — it's a different *notation* for the same procedure, in which "confidence" is a margin in bits (directly interpretable: "grouping by `type` saves 340 bits") and priors are code designs. It's especially natural for record-vs-map, where the tradeoff *is* literally a coding tradeoff: a record pays for its field vocabulary once in the model and near-nothing per sample; a map pays nothing in the model and a key-string code per entry per sample. **Same coverage as (c).**

**(e) Discovery-rate / Good–Turing vocabulary estimation.** Not a whole formalism, but the correct estimator for a sub-question that recurs in *three* of the four failures: "have I seen the whole vocabulary?" Good–Turing puts the unseen mass at ≈ `f₁/N` (singletons over sample count); Chao1 lower-bounds true richness at `S_obs + f₁²/(2f₂)`. That question is enum member-set completeness (failure 4 — this *is* the missing coupling), object-key vocabulary boundedness (failure 1), and unseen-variant count (failure 2's variant recall). The survey's own synthesis gropes toward this under the name "Zipf-aware weighting" — "treating a field's value-frequency distribution shape, not just its raw cardinality, as enum evidence" — and flags it as unevaluated. JSONoid's HyperLogLog (§4) answers the adjacent cardinality-at-scale question but not the completeness one.

### 1.6 Reading

(c) and (d) are the same procedure in two notations, and (e) is an estimator that lives *inside* their likelihood terms rather than a rival. Read narrowly (as originally written), the real question isn't which of five, it's: **which notation do we write the scoring functions in.** Tradeoffs, impartially:

- *MDL*: no explicit prior elicitation; every knob is a code-length choice defensible by universal-coding arguments; margins in bits are legible in debug output and in `meta`. Cost: code design is prior specification wearing a different hat, and someone has to design the codes.
- *Bayesian*: priors are explicit and therefore honestly user-facing (which is exactly what question 2 asks for); posteriors are calibratable and testable. Cost: more surface to elicit, and normalizing constants across a heterogeneous hypothesis space need care.

Read at the level §1.2–1.4 arrive at, the question generalizes one step further: it isn't just which notation to score in, it's that "hypothesis," "score," and "prior" all turn out to be facts and syntheses of facts, and the MDL/Bayesian equivalence above is a special case of the more general claim that a decomposition's *cost* (in whichever notation) is itself just a fact computed deterministically from the facts it costs.

## 2. "Dirty data" formally, and what belongs to the user

### 2.1 A generative model

At a position, model the corpus as a two-component mixture:

- with probability `1−ε`, an observation is drawn from the true schema: variant `k` with proportion `θ_k`, where `θ ~ Dirichlet(α)` over variants;
- with probability `ε`, it is **contamination** drawn from a broad noise distribution `Q` — ptype's X-factor PFSM (§2), deliberately given the widest possible alphabet so it assigns *some* nonzero probability to anything but always less than a specific type would to a well-formed value.

Per-value posterior: `p(noise | v) = ε·q(v) / (ε·q(v) + (1−ε)·Σ_k θ_k·p_k(v))`. The schema-level question — "is variant k real?" — is then a model comparison: does admitting variant `k` into the schema buy more than explaining its observations as contamination costs?

### 2.2 Why skew alone provably cannot decide this

Both hypotheses predict a small minority count. That's why `majorityRatio > 0.9` measured a significant *harm* to union recall (p=0.0005): it always pays the cost of collapsing a rare-but-real variant, and this session's case set contains no corpus where the minority is genuinely off-schema, so it can only ever show the downside. The discriminating signals *do* exist in the data and are simply unused:

1. **Concentration of the minority.** Five samples that are all `"N/A"` are five draws of one thing; five samples that are five distinct random strings are five draws of noise. Identical skew, opposite conclusion. Formally, a real variant is a *low-entropy* explanation, contamination is *high-entropy by construction*. `node.values` already retains everything needed to compute this — the current code just counts.
2. **Prior mass.** Under `Dirichlet(α)` with small α, a rare variant is a priori plausible; with large α it isn't. That's a single interpretable dial.
3. **Sentinel vocabulary.** ptype's curated missing-data alphabet (`-1, -9, -99, "", " ", "NA", "NULL", "N/A", NaN`) — §2 calls this "disguised missing data" after Pearson (2006). A value's *identity* is evidence of contamination independent of its count. The survey already lists this as adoptable ("a curated missing-value-sentinel alphabet... as a first-class detector, distinguished from 'this field is genuinely nullable'").
4. **Cross-position correlation.** Contamination is usually per-*record* (one bad row has several bad fields); a real variant is coherent. **This one is not currently observable** — evidence is gathered per position with no sample provenance. Flagging it as an evidence-layer gap, not an available signal.

### 2.3 The configuration split

**User-stated (honest priors, domain-meaningful):**
- expected contamination rate `ε` — or a `Beta` prior on it ("I think roughly 1% of these log lines are junk; I'm not sure").
- **asymmetric loss**: the cost of dropping a real variant vs. admitting noise into the schema. This is the decision-theoretic knob that *replaces* `0.9` — and unlike `0.9` it has a meaning the user can actually hold an opinion about.
- vocabulary concentration `α` (equivalently: "I expect a handful of variants" vs. "I expect many").
- optionally: a domain sentinel vocabulary; a domain-specific `Q`.

**Algorithm-assumed (documented, not user-facing):** i.i.d. sampling given the schema; contamination independent per observation; the functional form of `Q` (broad/diffuse over the observed domain).

**Output changes from a silent collapse to a report:** posterior contamination rate, per-value posteriors for the flagged observations, and a decision taken *under the stated loss*. This is the survey's own §2 recommendation, verbatim: "let corpus-level inference *report* outlier rate rather than silently absorbing it into the type."

**Honest caveat.** `ε` and the loss ratio are still numbers. The claim is not that configuration disappears — Tagger's finding that no threshold generalizes across datasets (§1) is exactly the argument that it *must not*. The claim is that there is one small set of numbers, on interpretable scales, whose mapping to behavior is *derived* rather than hand-tuned per pass — replacing eleven algorithm-internal cutoffs in `ResolveStrategy` whose interactions nobody can reason about.

## 3. Does one framework subsume all four? (No — three yes, one no)

*(Language note: this section predates the facts/synthesis framing in §1.2–1.4. Where the original text below says "hypothesis," read it as "candidate fact" or "candidate decomposition" — the conclusions are unaffected; only failure 2's characterization needed an actual correction, noted in place below.)*

**Failure 1, dict-vs-record: YES, cleanly.** This is the best case for the whole argument. Under MDL, "record over vocabulary F" pays `|F|` key-strings once in the model and ~0 per sample; "map" pays nothing in the model and a key code per entry per sample; a third hypothesis, "fixed fields + open map," is scored on the same scale rather than reached via the current `commonKeys.size > 0` special case. Equivalently in Bayesian terms: a CRP/Dirichlet-process predictive over keys has expected distinct-key growth `~ α log N` and **never plateaus**, while a fixed-vocabulary multinomial saturates. Discriminating `[3,9,13,16,17,18,18,19,20,20,20,20]` — zero new keys in the last four of twelve, i.e. `f₁ → 0` — from a CRP is a likelihood computation that the plateau dominates, and it is exactly the information the endpoint ratio 1.4167 discards. The full per-sample key sequence is **already collected** (`EvidenceNode.object.keySets`, in corpus order); `walkAndDetectDicts` throws it away at line 1470. Secondary benefit: this makes Baazizi's K/L equivalence (§5) a *scored* per-location choice rather than a global parameter — the survey already names automatic-per-location K/L selection as our point of departure from Baazizi 2017/2019/2020, and MDL finally supplies the criterion that departure was missing.

**Failure 4, enum under Zipf: YES, and it's the same machinery.** Under a Dirichlet-multinomial (or Pitman–Yor, which is the right model for Zipfian tails) over a position's value frequencies, one posterior computation yields both quantities that are currently divorced: (i) `p(closed small vocabulary | data)` vs. `p(open vocabulary)` — the shape question `enumDetection` measures; and (ii) the predictive probability of an unseen member, i.e. Good–Turing's `f₁/N` — the completeness question `enumMemberFidelity` measures. They are coupled *because they are marginals of the same model*: high discovery mass should temper the shape claim, and at minimum must be reported alongside it. The pathology the harness found — skew makes (i) look better and (ii) worse at the same N — becomes the model doing the right thing: skew raises tail singleton mass, which lowers completeness, which propagates. **Required evidence-layer change**: `EvidenceNode.distinctValues` is a `Set`, so `f₁`/`f₂` are *not derivable today*. This needs value frequency counts. It is the one genuinely necessary change below the resolution layer.

**Failure 3, dirty data: YES**, per §2 — this becomes a mixture posterior instead of a threshold, and the decisive signal (minority concentration vs. diffusion) is already sitting in `node.values`. So this is a wrong-decision-procedure failure and the formalism does fix it. The residual — cross-position correlation — is a refinement, not a requirement.

**Failure 2, envelope-pattern DU: NO. Not by formalism alone.** This is the one the brief was right to suspect. As measured, separation for `{type, data:{…}}` is **identically 0** for every candidate at every N: the feature is constant, not mis-scaled. A better decision rule over the same feature cannot help. What's needed is a **hypothesis-space and search-scope change**: the candidate "condition on field `f`" must be scored by how much conditioning on `f`'s value reduces the residual entropy of the sibling subtree it's meant to discriminate, not by a flat distance between immediate sibling key sets. Precisely: this quantity is the **mutual information between the candidate field `f` and the residual entropy of its sibling subtree(s)** (§1.4) — a corrected characterization of the fix; an earlier pass at this document described the needed change as "the recursive description length of the whole subtree" scored under the grouping, which is close but not quite it, since a subtree can be short to describe (low absolute description length) without `f` being what's *causing* the reduction. Mutual information is the quantity that isolates the causal contribution of conditioning on `f` specifically, which is what "is `f` a meaningful discriminant" actually asks. Under either framing the fix falls out for free once computed *recursively rather than flatly* — grouping by `type` turns `data` from one nine-field all-optional union into five tight records, and mutual information between `type` and `data`'s shape is high because that collapse is real — **but only because the quantity was scoped to the whole subtree instead of the immediate sibling key sets.** Two distinct changes, and the second is not implied by the first: a correct formalism applied at the wrong tree depth is still wrong. The framing that unifies it: today's `cohesion × separation` is a *flat proxy* for "how much does conditioning on `f` explain," and it happens to be degenerate on an important real-world class (every envelope-shaped API — Stripe, most webhook systems, JSON-RPC). Mutual information / MDL compute that quantity exactly and recursively. So the formalism supplies the right currency; the search scope is a separate, real piece of work.

**A fifth benefit none of the four failures names, worth stating because it's the strongest architectural argument.** Pass *ordering* currently arbitrates between mutually exclusive interpretations — the CFD pass "runs only after `tryDetectDU` has had first refusal," splitting "runs after dict detection (not before)," and so on, each documented with a plausible local rationale and no global criterion. Under the fact/synthesis model this dissolves: all candidate decompositions at a position are scored in one currency (marginal entropy reduction) and the best wins. That's not a patch to any of the four failures; it's the removal of the mechanism that made them individually invisible.

## 4. Architecture

### 4.0 What changed here since the original draft

The original version of this section built the architecture around a single `score(hypothesis)` primitive: enumerate candidate hypotheses at a position, cost each, keep the cheapest. §1.2–1.4 above replace "hypothesis" with "fact," and replace "enumerate candidates, then score" with "facts are synthesized from simpler facts, and a decomposition is accepted or rejected by whether it reduces residual/marginal entropy." §4.1–4.3 below rebuild the architecture on that substrate. The practical difference from the original draft is smaller than it might sound — most of what changes is what the core primitive is named and what it returns, not the surrounding system (evidence collection, the eval harness, `unifyTypes`, in §4.4 below, survive essentially as originally described).

**A gap this substantially narrows, but does not close.** The original §4/§5 flagged composite/multi-field discriminants and cross-position dirty-data correlation as needing "graph edges" beyond the evidence tree — machinery this document did not design. §1.3's content-addressed fact model narrows that gap: because facts aren't required to be anchored to a single tree position, a fact scoped at "this sample" or "this corpus" rather than "this position" can express cross-position relationships without a separate edge-graph data structure bolted onto `EvidenceTree`. That is a real simplification of the *kind of machinery needed*, but it is not yet a design: something still has to decide, for a given fact, what its correct scope is (single position vs. sample vs. corpus), and that assignment rule is unspecified here. Treat this as "the missing piece got smaller and better-shaped," not "the missing piece is gone."

### 4.1 The substrate: facts, synthesis, and the marginal-entropy-reduction criterion

Everything is built from three parts instead of one scoring function:

```
synthesize(facts: Fact[]) -> Fact
  // pure, deterministic, content-addressed: same input facts -> same output fact,
  // always. This is the operation from §1.3 — the one place "combine evidence" happens.

entropyReduction(explanation: Fact, residual: Fact) -> number
  // marginal/residual entropy of `residual` after conditioning on `explanation`,
  // in bits. This is the one criterion from §1.4 that decides whether a candidate
  // decomposition is worth keeping — MDL's L(V|H), mutual information, and
  // Good-Turing discovery mass are all instances of this one function evaluated
  // on different fact pairs.

rules: DecompositionRule[]
  // condition(s) -> conclusion, per §4.2 below. Enum, dict, DU, CFD, and
  // dirty-data become rule families that produce candidate facts for
  // synthesize/entropyReduction to evaluate, replacing "hypothesis families
  // registered against a scoring primitive."
```

A resolution step at a position: candidate decomposition rules propose candidate facts (conditional or unconditional, per §4.2); `entropyReduction` scores each candidate against the residual it would leave; the search keeps the decomposition that reduces residual entropy the most (with a runner-up margin, as before); `synthesize` folds the accepted decomposition's facts, together with its children's already-synthesized facts, into the fact returned to the parent. Recursion happens because a child's facts are inputs to its parent's synthesis, not because a parent hands children a hypothesis to be scored under (the original framing) — the effect on failure 2 is the same (children are evaluated in the context their parent's candidate decomposition creates), but the mechanism is now "facts compose upward through synthesis" rather than "children are costed under the parent's chosen hypothesis." Today's architecture has six independent walkers, each re-traversing the tree and each able to overwrite the last; that becomes one traversal, one substrate, and one criterion.

### 4.2 Decomposition is form-agnostic, not literally a decision tree

An earlier pass at this design took "decision tree" as the literal target shape for the whole type system: a predicate tests some observed property of the data and branches to mutually exclusive children, each ultimately terminating in a complete type. That framing was explored and then explicitly walked back, because it does not fit every `TypeRef` kind:

- **Object** and **discriminated union** genuinely fit branch-and-test: field presence, or a discriminant's value, partitions the samples into mutually exclusive groups, each scored and recursed into independently.
- **Enum** fits too, as a flat multi-way test directly on the value rather than on a derived predicate.
- **Primitive** is the base case — no further decomposition applies.
- **Map/dict** does **not** fit as "a branch with one observed outcome" — a framing that was considered and explicitly rejected. There is no per-key *test* being evaluated at all: every key, seen or unseen, unconditionally maps to the same value type `V`. This is a categorically different kind of rule from DU's or object's: an **unconditional** conclusion, not a conditional branch that happens so far to have only one observed branch. Zero-way testing (no test at all) is not the same thing as one-way testing (a real test with exactly one outcome observed to date) — collapsing the two would silently reintroduce the "map is a single-branch decision tree" framing that was rejected for good reason: a map's rule doesn't get more branches as more distinct keys are observed, the way a genuinely-narrow enum or DU would.
- **Array** similarly resists branch-and-test: the same element-type rule applies uniformly to every element regardless of any per-element property, so there's no discriminating test to speak of. This is closer to **recursive self-reference** than to a decision at all — the same shape the existing IR already uses for recursive types like `TreeNode { children: TreeNode[] }` — an array's element rule refers back into the same synthesis process rather than branching out of it.

The principle that survives, stated precisely: **a decomposition rule is `condition(s) → conclusion`, where the condition set may be empty (an unconditional rule — map's "any key → V") or non-empty (a conditional rule — DU's "if `type == X` then shape is Y"), and the conclusion may be a partial fact/refinement rather than always a complete terminal type** — conclusions compose together via synthesis to build up the full picture, rather than every path necessarily terminating in one self-contained answer at a leaf. Decision-tree branching — conditional, mutually exclusive, hierarchical rules whose leaves are complete types — is the special case where a family of rules happens to have all three of those properties. It is not the general shape every `TypeRef` kind reduces to, and treating it as though it were is exactly the mistake map and array expose.

**What this means concretely:** the previously-separate detection passes (enum, dict, DU, CFD, dirty-data) are not four different algorithms needing four different scoring conventions — they are four different **rule families**, each contributing conditional or unconditional decomposition rules, all sharing the same fact substrate (§1.2), the same synthesis operation (§1.3), and the same marginal-entropy-reduction criterion (§1.4, §4.1) for deciding whether a proposed decomposition is worth applying.

### 4.3 What the substrate leaves open

Consistent with §1.3's caveats: this substrate specifies how candidate facts *combine and get scored* once proposed (`synthesize`, `entropyReduction`), and it specifies the *shape* candidate rules may take (§4.2). It does not yet specify the generation strategy that produces the *next* candidate rule/fact to try at a position, nor the eviction policy for facts under memory pressure during search. Both remain open design work, carried forward into the phasing in §5.

### 4.4 What survives, what changes, what's new

**Survives essentially intact — `collectEvidence` / `EvidenceTree`.** This is the good news and it's substantial: the phase-1/phase-2 split was already the right cut, and phase 1 already gathers per-position type counts, per-sample key sets *in corpus order*, per-field presence counts, raw values, and raw element objects — all of it already expressible as base-level facts under §1.2, no restructuring needed to call it that. Failure 1's entire signal is already there. Required additions: **value frequency counts** (for Good–Turing; failure 4's blocker) and, optionally, **per-sample provenance indices** (for cross-position contamination correlation, though see §4.0's note that this may partially fold into fact scoping instead of a dedicated provenance field). Neither is structural.

**Survives and becomes central — the eval harness.** `inference-eval.ts` and `stats.ts` are not collateral; they are the *acceptance mechanism* for every phase below. `runEvaluationTrials`' seed derivation (`name:n:trial`) was purpose-built so two configurations share corpora index-for-index, which is exactly what's needed to paired-bootstrap new-resolver-vs-old. `ablationRunner` generalizes from per-toggle to per-rule-family. `realistic-corpora.ts` becomes the regression fixture set with baseline numbers recorded (GitHub Issue overallF1 0.876, npm package.json overallF1 0.280, Stripe webhook overallF1 0.472) to beat. **One genuine addition needed**: a *calibration* axis. If the engine emits posteriors, the harness must check that 0.8-confidence claims hold ~80% of the time — no current axis measures this, and an uncalibrated posterior is worse than an honest threshold.

**Survives as the fact-synthesis step that builds the final `TypeRef` — `unifyTypes`/`mergeAll`.** Baazizi's `Fuse`/`LFuse` (§5) is still what builds the `TypeRef` once a decomposition is accepted; under §4.1's vocabulary it is one concrete implementation of `synthesize` for the specific case of merging sibling type facts. The survey notes we've never stated or tested its commutativity/associativity, which Baazizi proves as Theorems 5.4/5.5; that gap gets *more* consequential under a substrate that leans on synthesis being order-independent (§1.3's determinism claim assumes it), so it's worth closing (fast-check is already in the package per `from-json.fuzz.test.ts`).

**Replaced — `ResolveStrategy`.** Eleven threshold constants collapse to a small `InferencePriors` (noise rate, loss asymmetry, vocabulary concentration, minimum-evidence floor) plus escape hatches. `customResolvers` becomes "register a custom decomposition rule family," which is strictly more expressive than today's post-hoc override hook.

**Genuinely new:** a bits/cost calculus (universal integer codes, string codes, Dirichlet-multinomial marginal likelihoods, CRP predictive) implementing `entropyReduction` — small, pure, unit-testable in isolation; a per-position candidate-fact generator (the open problem named in §4.3 — this is genuinely new design work, not a port of the old hypothesis enumerator); the recursive search with memoization (and, per §1.3, eviction of facts under memory pressure); and a confidence surface on output `meta` (chosen decomposition, runner-up, margin) — which is also what makes the engine debuggable, and matches the transparency Tagger's demo explicitly showcases to build user trust (§1).

## 5. Effort, risk, phasing

**Scope, honestly:** this is *predominantly* a `resolveEvidence` redesign, but not purely. One required evidence-layer change (value frequencies), one optional (sample provenance). `collectEvidence`'s structure survives; its output grows.

**Risks:**

- **Search blowup.** Recursive scoring where a parent decomposition rule reshapes children's grouping is exponential if done naively. §1.3's bounded-memory-via-re-derivation argument is a principled mitigation for the *memory* half of this risk (evict and recompute rather than hold the whole search tree resident), but not for the *time* half — the number of candidate decompositions explored still needs bounding. Mitigations: keep Tagger's unary discriminant restriction (which it imposes for exactly this reason, §1 — CFD discovery "scal[es] exponentially in the number of attributes"), greedy top-down with memoized child costs, cheap gates before costing. **Must be measured** — this session already hit an O(n³) surprise in complete-linkage clustering (6.9s → 52ms at n=500 after a rewrite).
- **The arbitrariness relocates, it doesn't vanish.** MDL moves judgment into code design. The defensible claim is that the choices become fewer, principled by universal-coding arguments, and *globally consistent* so candidate decompositions are comparable. It is not "no magic numbers," and this doc says so plainly.
- **Candidate generation and eviction policy are still open** (§4.3). The phases below assume a workable generation strategy and a memory-pressure eviction policy exist by the time P4's search-cost work lands; neither is designed yet.
- **Regression ambiguity.** ~3,200 lines of tests encode current behavior (`from-json-corpus.test.ts`, `from-json.adversarial.test.ts`, `from-json.fuzz.test.ts`). Some expectations *should* change — that's the point.
- **Calibration is unproven until measured.**
- **Small N is genuinely hard, and no formalism rescues it.** At N=5 the posterior is prior-dominated. `docs/roadmap.md` already names "confidence scaling at low sample counts" as an open design question; this is where it lands, and it lands as a policy choice, not a solution.

**Phases** (mirroring the 5-phase eval-rigor plan that shipped this session — each lands real, green code):

- **P0 — ratification, no code.** This document plus owner decisions (see "Resolved decisions" below).
- **P1 — cost calculus + evidence addition.** New pure module (`description-length.ts`), unit-tested against hand-computed bit counts; add value frequency counts to `EvidenceNode` (behavior-preserving). No integration. Ships green.
- **P2 — first family end-to-end: record vs. map vs. mixed.** Behind `resolver: "heuristic" | "model"`, defaulting to heuristic. Acceptance gate: package.json overallF1 moves off 0.280 with fieldCoverage recall off 0.06, *and* paired-bootstrap shows no `dictDetection` regression on the generated harness. This is failure 1, the cleanest case, and therefore the right proof of concept.
- **P3 — vocabulary family: enum shape ⊕ member completeness, jointly.** Dirichlet-multinomial + Good–Turing, emitting a completeness confidence. Acceptance: the zipfian paired test flips from "shape better / members worse" to a single coupled, calibrated report.
- **P4 — grouping family: DU / CFD / structural split unified**, scored by mutual information between the candidate discriminant and residual sibling-subtree entropy, computed recursively rather than on immediate sibling key sets (§1.4, §3's corrected failure-2 characterization). This is where failure 2 is fixed and where the search-cost work lives. Acceptance: Stripe `unionFidelity` 0.00 → recovers `event` as a 5-variant DU.
- **P5 — noise model.** Contamination mixture with user-stated `ε` and loss, replacing `walkAndDetectDirty`. Acceptance: the p=0.0005 recall harm reverses on the dirty-outlier profile **and** a *new* generator profile with genuinely off-schema contamination — which the current case set cannot construct, as that test's own comment concedes ("This ablation set has no case where a corpus is contaminated with values that are genuinely NOT part of the schema") — demonstrates the intended upside.
- **P6 — flip the default,** deprecate the per-pass thresholds, record calibration numbers, update the survey's Synthesis.

## Resolved decisions (2026-07-25)

- **Current heuristic behavior is NOT contractual.** Correctness is prioritized over preserving existing pass/fail behavior. This means later phases (P2-P5) are free to be behavior-changing, not required to be strictly additive — the eval harness (paired bootstrap against the realistic corpora baselines) is the acceptance gate, not "does old behavior still hold."
- **Confidence surface on `meta`: approved.** The engine will emit chosen hypothesis, runner-up, and margin on output `meta`. This is additive to the `TypeRef` contract (a new optional field, not a breaking change to existing consumers).
- **`clusteringMethod`'s fate: deferred to P4.** Whether it's fully subsumed by the new grouping-family architecture or survives as a user-facing override will be decided when P4 is actually built, not speculated now.
- **Small-N policy: resolved as "commit to the conservative/coarser hypothesis, not abstain."** Not "refuse to output anything when confidence is low" and not "commit aggressively with a low-confidence label" — instead, when confidence is low, the engine should prefer the less-specific/less-risky hypothesis (e.g. widen rather than over-commit to a narrow guess). Concretely: a single-sample package.json corpus should still produce an approximately-correct schema, not an empty/refused result — this mirrors how single-value inference (`fromJson`) already never commits to a `literal` type from one sample, extended as a general principle to corpus-level low-confidence cases. This directly informs the calibration work in P1/P3: "low confidence" should route toward a coarser hypothesis in the same hypothesis family (e.g. `string` instead of a premature `enum`, a merged record instead of a premature narrow split) rather than an abstention/error state.
- **MDL vs. Bayesian notation: leaning Bayesian for user-facing surfaces** (priors/posteriors are more directly interpretable for a person stating "I expect ~1% noise" than a bit-margin), **MDL acceptable for internal implementation** where bit-additivity is convenient. Explicitly low-stakes — the two are mathematically equivalent per §1.6, so this doesn't constrain P1-P6's actual algorithms, only the vocabulary used in code/API/docs. Not a hard requirement, just a documented leaning.

## Discussion log (2026-07-25)

Sections 1 and 4 above were substantially revised in a second pass, after the P0 ratification recorded in "Resolved decisions" above. The revision emerged from an extended design conversation with the project owner, not a unilateral rewrite — recorded here so a future reader can trace why the document's core vocabulary shifted mid-stream.

The conversation worked through, in order:

1. **Facts vs. hypotheses.** The original §1 framed inference as choosing among competing hypotheses, scored by likelihood/MDL. This left "how do candidate hypotheses get proposed" as an unaddressed prerequisite to scoring. Replacing "hypothesis" with **fact** — a deterministically-derivable statement about the corpus, with scores/costs themselves just facts computed from simpler facts — dissolves the proposal problem: facts are derived, not proposed from a pre-bounded space.
2. **Synthesis as a Merkle-like operation.** Facts combine into more complex facts via **synthesis**, argued to be pure, deterministic, and content-addressed — directly analogous to git objects, Nix derivations, and Bazel's build cache. This yields structural sharing (identical facts derived at different tree positions collapse by content, without a separate cross-position edge graph) and bounded memory (facts can be evicted and re-derived on demand, rather than held resident through search). Both were recognized as answers already implicit in the model to gaps the original document had flagged as unresolved (cross-position correlation needing "graph edges"; search blowup as a flagged risk) — not new mitigations layered on top.
3. **Marginal entropy as the unifying refinement criterion.** Working back through all four diagnosed failures (§3) against the question "does the residual uncertainty after conditioning on the current explanation represent structure still missed, or variation already accounted for," each failure turned out to be an instance of one quantity — residual/marginal entropy — rather than four unrelated local statistics. This was recognized as generalizing, not replacing, the original MDL and Good–Turing candidates: residual entropy given an explanation is MDL's `L(V|H)` by Shannon's source coding theorem, and discriminant selection via entropy reduction is mutual information, which is also decision-tree information gain.
4. **Decision-tree-as-one-instance, not the target shape.** An initial attempt to state the general decomposition principle reached for "decision tree" as the literal structure everything reduces to. Working through each `TypeRef` kind against that framing surfaced that map and array don't fit branch-and-test at all (map's rule is unconditional — "any key → V" — not a one-branch test; array is closer to recursive self-reference than to a decision). The framing was walked back to the more general "condition(s) → conclusion, conditions possibly empty, conclusions possibly partial," of which decision-tree branching is the conditional/mutually-exclusive/hierarchical special case.
5. **A specific correction to §3's failure-2 characterization.** An earlier description of the envelope-pattern DU fix — "recursive subtree description length" — was flagged by the project owner in a later exchange as not quite precise: subtree description length can be short without the candidate discriminant field being what causes the reduction. The corrected characterization is mutual information between the candidate field and the residual entropy of its sibling subtree, which isolates the causal contribution specifically.

Sections 3 and 5 were updated only where they referenced the superseded "hypothesis family" vocabulary or the imprecise failure-2 characterization; their substantive conclusions (three of four failures subsumed, the phase structure and acceptance gates) were not revisited and stand as originally ratified.
